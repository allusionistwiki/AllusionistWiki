Playground（遊び場）: 仮説自由記述層

NOTE

この節は Wiki1 内の遊び場（Playground）です。ここに書かれた記述はすべて仮説（Hypothesis）または思考の痕跡であり、確定した事実ではありません。事実として引用しないでください。

この Wiki の正規層（Core）が「検証済みで信頼できる知識」を置く場なのに対し、Playground は スキーマ検証（Lint）を受けない自由な Markdown で、マクロな考察・仮説のブレインストーミング・LLM との対話ログを置く場です。「作品全体の神話的構造」のような超近視眼的な問いを、型にはまらずに書き始める場所として使います。

ルール

項目Core 層（正規層）Playground（本節）
記述形式厳密なスキーマ準拠（ID 体系 E_ / A_ / MY_、Lint 必須）自由な Markdown（Lint 対象外）
記述の地位検証済みの知識仮説・思考の痕跡（未確定）
目的信頼できる知識の保存・公開・GraphRAG ソース探索（Exploration）と創発
引用事実として引用可出典として引用不可（昇格後にのみ可）

Playground 内のページは自由に作成・改変して構いません。代わりに、冒頭に状態ラベルを付けて「これは事実ではない」ことが視認できるようにします。

状態ラベル（語彙）

状態意味
draft書きかけのメモ
exploring検討中（LLM 対話ログを含む）
promotion-candidate昇格候補 — Core 層の主張（A_）に翻訳する価値があると判断した仮説
promoted昇格済み — Core 層に正式な主張として反映された（反映先の ID を記載）
discarded破棄 — 検証に耐えなかった記録（来歴として残す）

使い方

  1. 新しい仮説を書く: 本页の 仮説メモの書式テンプレート をコピーして content/playground/ 直下にページを作成
  2. LLM との対話ログを貼り付けて検討してよい（対話の要点を「材料」節に整理する）
  3. 考察の材料には Core 層の確定済み事実（エンティティ E_・主張 A_・伏線 MY_）を使ってよい。事実を無視した飛躍には「根拠なし」と注記する
  4. 「本物の洞察だ」と思えたら状態を promotion-candidate にし、本页の 昇格プロトコル の手順で Core 層への昇格ドラフトを起こす

昇格（Promotion）プロトコル — Playground と Core をつなぐ橋

本页は設計図のたたき台（設計案）であり、実装された仕組みではありません。 ここに書かれた手順は人間が手作業で運用する前提の合意形成用ドキュメントです。自動化（Promotion Agent 等）は将来の検討対象です。

1. 二層アーキテクチャ（Two-Tier Architecture）

Wiki1 の自由で有機的な創発性と Wiki2 の厳密で堅牢な構造化は、一つのフォーマットに混ぜようとするから難しいのであって、役割とフェーズを分けた二層として設計すれば共存できる、という構想です。

層場ルールフェーズ
Layer A: Playgroundcontent/playground/スキーマ検証なし・自由 Markdown探索（Exploration）・創発
Layer B: Core正規層（content/claims/ 等）厳密なスキーマ準拠・ID 体系（E_ / A_ / MY_）・Lint 必須活用（Exploitation）・保存

Wiki1 / Wiki2 の統合スキーム（未構築）は、この二層の分離を前提に「橋」の側で統合する方向性を想定しています。

2. 昇格（Promotion）の 3 手順

Playground で生まれた仮説を、Core 層の正式な分析主張（A_）へ昇格させる手順。

  1. 発見 — 人間が Playground の記述から「本物の洞察（Insight）」を感じ取る（状態を promotion-candidate にする）
  2. 翻訳（LLM 支援） — その自由文を選択し、Core 層の主張スキーマ（subject / predicate / object + 典拠）へ変換した昇格用ドラフトを LLM に生成させる。原文引用（¶ 出典）は Core 層の既存データから補完させる
  3. 承認とマージ — 人間がドラフトを確認（Human-in-the-Loop）し、問題なければ Core 層へ PR として投稿。機械ゲート + LLM 監査（既存の機械ゲート + LLM 監査パイプライン）を通って公開され、review_status: human_verified となる

Lab での実運用では、手順 3 は既存の「直接編集（PR）」経路そのものを使います。昇格専用の新しい受け口は作りません。

3. 逆方向のフィードバック（文脈の注入）

Playground を「ただの妄想の場」にしないための仕組み。

  • Playground で考察を始めるとき、Core 層の確定済み事実（E_char_* のエンティティ、A_* の主張、MY_* の伏線）を材料として先に読む
  • 将来は GraphRAG が関連事実を自動収集して LLM への背景知識（Context）として注入する想定。Lab 段階では手動で読むことで同じ効果を得る
  • 注入した材料に対しては「根拠なし」注記の免除、未収集の飛躍には注記、という線引きを Playground 運用則 と共通させる

4. 想定ワークフロー

運用内容
日常Core 層のパイプラインが章ごとの事実を淡々と抽出・蓄積する（退屈だが正確な作業は AI）
ひらめいた時オーナーが Playground で Core 層の事実を材料に作品全体の構造について対話する（型にはまらない）
収穫生まれた仮説を A_ スキーマへ翻訳し、Core 層に確定知識として保存する（昇格）

「Wiki1 の魂（創造性）」を殺さずに「Wiki2 の肉体（堅牢性）」を持つ、という狙い。

5. 現状の合意と未決事項

合意（本页で置くもの）

  • Playground の場は content/playground/ に確保済み（Playground 運用則）
  • 昇格は新規受け口を作らず既存の PR / llm-task 経路で行う
  • Playground → Core への参照方向制限（Playground の記述を正規層から引用しない）

未決（将来の検討）

  • 昇格ドラフト生成の自動化（Promotion Agent）— 手動で数回昇格を試し、板についてからスクリプト化する
  • Playground ページのスキーマ（現状は自由記述。状態ラベル以外の必須項目を作らない）
  • GraphRAG による文脈注入（Core 層の検索基盤が整ってから）
  • Wiki1 / Wiki2 本体間での Playground の置き場所（Lab で運用が板についてから本番設計へ）

仮説メモの書式テンプレート（コピー用）

以下のブロックをコピーして content/playground/<任意のページ名>.md に保存し、角括弧のプレースホルダを埋めて使ってください。frontmatter の status は 状態ラベル の語彙（draft / exploring / promotion-candidate / promoted / discarded）から選びます。

使用上の注意

  • 本文は自由記述です。Lint・スキーマ検証の対象外（Playground 運用則）
  • 状態が上がったら（promotion-candidate 以上）昇格プロトコル の手順に従う
  • 原文（小説本文）の長文引用はしない（引用は本番運用と同じく最小限の抜粋のみ）
